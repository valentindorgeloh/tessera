## 1. Root cause (hydration error 418)

The investigators agree on the defect. Three of them reproduced it in scratch copies: the
dev investigator on ports 3611 and 3612, the code investigator on 3613, and the sweep on
3614 and 3615.

- What happens: someone presses the top-bar "Collapse sidebar" button, or `mod+b`, after
  the shell has hydrated but while the streamed sidebar Suspense boundary is still
  dehydrated. The boundary is `(tessera)/layout.tsx` l.33: `<Suspense
  fallback={<SidebarSkeleton/>}><SidebarData/></Suspense>`, passed to the shell as `sideNav`.
  When that boundary later hydrates, `Sidebar` reads the new `isNavCollapsed=true` from the
  `ShellContext`. The server HTML was rendered expanded, so Astryx `SideNav` renders a
  different structure. `SideNav.js` l.223 sets `showResizeHandle = isResizable &&
  !collapsed`, and l.406-424 add the wrapper `<div class="x1n2onr6 ...">` only when the nav
  is expanded. On the client the `<nav>` appears where the server HTML has that wrapper
  div. React throws `throwOnHydrationMismatch` (minified #418, args `HTML`), client-renders
  the boundary, and the page ends up correct: the nav is 48 px and the button reads "Expand
  sidebar". One pageerror is reported.
- Why React does not prevent it (code investigator, instrumented React 19.3.0 dev bundle):
  1. The boundary's element comes from the RSC payload, so its props are identical on every
     shell re-render.
  2. `attemptEarlyBailoutIfNoScheduledUpdate`, case 13 with `stateNode.dehydrated` set,
     returns without calling `propagateParentContextChanges`.
  3. Lazy propagation never walks into the boundary, because every ancestor re-renders.
     `TesseraShell` holds the state, there is no React Compiler, and `ShellFrame` consumes
     `AssistantContext`.
  4. Selective hydration therefore never runs, the toggle commits, and the boundary later
     hydrates at OffscreenLane with the new value.

  React 19.3 no longer has error #421; neither bundle contains it.
- Scope: the defect is in the shell and does not depend on the route. Home and its Since
  rows are not involved. The sweep reproduced it on 25 of 25 routes in at least one mode at
  1440. With the toggle, delay 2500 ms reproduced it on 12 routes, 800 ms on 19 and CPU x6
  on 23. With `mod+b` polling the counts were 14, 10 and 14. Light and dark both reproduce.
  It never occurred at 375, where the sidebar is the drawer and the collapse state does not
  change the SideNav markup. It never occurred without an interaction (0 of 150 cases), and
  never on a search, help, account or nav-row click (those do not change shell context). The
  wording in `docs/improvements.md` l.12 and field-guide l.79 ("dehydrated Home content",
  "only with Since rows") is wrong. Home only widens the window.
- Where the investigators seem to disagree, I re-checked the code. They do not contradict
  each other:
  - Reading `useSyncExternalStore` (uSES) in the provider does not fix it (dev
    investigator, option 2). Reading it in the consumer does (sweep prototype). In the
    provider the value still travels through a changing context, which is the same miss. In
    the consumer, `mountSyncExternalStore` uses `getServerSnapshot` whenever the fiber is
    hydrating, at any lane. Then the passive store-consistency check re-renders it with the
    client value. The sweep measured this: after the store change `navWidth` was 48.
  - "A click as soon as the button is visible is dropped" (dev, code) and "an early click
    reproduces" (sweep, production) describe the trigger timing, not the cause. The
    reliable trigger fires in the first task in which the toggle has a `__reactFiber` key.
    That is the shell's hydration point, and the sidebar is usually still dehydrated then.
    The e2e lane uses that trigger.
- Other console errors: there were none. The sweep's 900 cases (25 routes, 1440 and 375,
  8 interactions, 3 modes) had no other console error, pageerror or HTTP >= 400.
- Latent, same mechanism, never reproduced: `AiStatusProvider` holds `status` in
  `useState(null)` and fetches it in an effect. Consumers under the server-passed
  `{children}` render differently once `status.available === true`: `SinceLastVisit` l.110
  (DigestCard), `ViewsScreen` l.55, `WorkspaceSettingsScreen` l.91 and `IntakeScreen` l.92
  (through `useAssistant().status`). The code investigator faked `available:true` in 9 runs
  (800 ms, 2500 ms, CPU x6), and Home always hydrated before the status arrived. The early
  Assistant button was never exercised, because the sweep servers had no AI fake. Per the
  task, these get regression tests only (e2e (f), (g)), and no fix this round. If one fails
  at verify, it becomes a reproduced defect for a fix pass.

## 2. Chosen fix and why

Move the collapse flag out of the changing `ShellContext` value into a small client store.
Every consumer reads it with `useSyncExternalStore(subscribe, get, () => false)` inside
`useShell()`. The server always renders the sidebar expanded, so the server snapshot is
the constant `false`. The context value then holds only stable callbacks and never changes
on a toggle. A boundary that is still dehydrated hydrates against the server snapshot,
which matches its HTML, and re-renders collapsed right after. This is the pattern the
sidebar already uses for its width and last project (`useSidebarResize`, `Sidebar.tsx`
l.126, l.156).

- Evidence: the sweep prototype (`r6-inv-sweep/shell-store-prototype.diff`, TesseraShell
  only) brought the failures to 0. Collapse at CPU x6 on /projects went from 6/6 to 0/6,
  `mod+b` polling at 2500 ms from 5/5 to 0/4, and Home with agent rows at CPU x6 from 4/4 to
  0/4. The code investigator's consumer-side `useHydrated` gate, the same React mechanism,
  went from 12/12 to 0/12. The prototype ran in dev only, so the verify phase repeats this
  on a production build.
- Why this fix over the others:
  - It removes the changing context, so no present or future `useShell()` consumer in a
    streamed subtree can hit this, and `Sidebar`, `SidebarSkeleton` and `TopBar` need no
    edit. A toggle also stops re-rendering the whole provider subtree.
  - The `useHydrated` gate (code investigator's 1b) covers only the consumers that remember
    to call it.
  - `startTransition` failed 11/12 and `React.memo(ShellFrame)` failed 12/12 (both tested).
  - Disabling the toggle until hydration drops user input and needs a disabled design.
  - Accepting the error leaves a real pageerror.
- What the user sees: a toggle that lands inside the window shows the button flipped to
  "Expand sidebar" while the sidebar stays expanded until its boundary hydrates, a few
  frames at most. Then it collapses.
- ASSUMPTION: collapse stays unpersisted (a reload starts expanded, as today; ui.md l.92).
- ASSUMPTION: the store is module-level, so the state survives a remount of
  `TesseraShell` in the same tab. The shell is mounted once in the layout, so nothing
  changes.
- Nothing writes the store on the server: it is written only from event handlers and the
  hotkey, and the server snapshot is a constant.
