# P4 research (views, settings, counts)

Collected 2026-10-11 by four read-only research agents on the merged tree, before the layout-rework merge commit. Input for the P4 contract; the first contract draft was lost when the temp scratchpad was cleaned. Facts cite file:line or public URLs (Plane docs only, no Plane code).

## Engine inventory

Plane's public docs cover these P4 topics: creating views (from a dialog or with "Save View" from Work items), "Update View" in the filter bar, unsaved changes being discarded, Duplicate ("Copy of"), Lock, Delete, favourites, access, Display (Group by, Sub-group by, Order by, Show sub-work items, Show empty groups), the States rules (default, delete, group-last-state, triage), the Labels rules (parent groups one level deep by drag, delete cascades to children), the General and Features tabs, and timezone. Several things the task asked about are NOT in any public doc. These are: the columns of the views list, its search and sort, a "Save as new view" action, how multi-valued group-by duplicates items, what dropping into an assignee or module group does, the identifier character and length rules, what renaming the identifier does to keys, what disabling a feature does to existing data, and counts in the sidebar or group headers. The docs say three things that matter for drag and drop: in Board, Sub-group by is supported (the views page says Board only); dragging a card between label groups on the board relabels it; and quick-add in a group takes that group's value. The engine already covers most rules: views.ts has duplicate with "Copy of", lock and unlock, and refuses to update or delete a locked view; group.ts duplicates items in multi-valued groups (labels, assignees, module) and add/remove on move; delete_state takes move_to_state_id; labels nest one level and deleting a parent deletes its children; getCounts has a view scope; project has *_enabled flags and agent_intake_required. P4 is therefore mostly UI (lane F) plus a few engine decisions. Sources are docs.plane.so, developers.plane.so (the API reference) and one forum.plane.so thread. No Plane source was read.

### Gaps

- Views list page: no public doc for the row contents (columns, icons, creator, date), search, sorting or filtering of the list. Tessera must design these itself; the P3 deferral 'Search, sort and filter on cycles and modules lists' also points to P4.
- No documented 'Save as new view'. Plane documents only 'Update View' and Duplicate. A Tessera 'Save as new view' (open the create dialog prefilled from the current unsaved state) is a reasonable addition but is not Plane parity.
- Locked view with temporary changes: the docs do not say whether the user may still change filters locally (unsaved) on a locked view. Recommend: allow local-only changes, hide 'Update View', show 'Save as new view'.
- Multi-valued grouping: no public doc confirms that an item with two labels, assignees or modules appears in both groups, or describes the None/'No labels' group. The only documented drop rule is that a board drag between label groups relabels the item. What a drop does to the other values (keep them, replace only the source value) and drops into assignee, module or None groups are undocumented.
- Group header counts and the default of 'Show empty groups' are undocumented.
- Project identifier: the length and character rules, uniqueness, and whether old keys keep resolving after a rename are undocumented. A forum report suggests keys are re-derived with no aliases. Decision 3 already fixes the pattern ^[A-Z][A-Z0-9]{1,11}$; keys are computed (decision 2), so /browse/NEW-12 works automatically, but /browse/OLD-12 does not unless Tessera stores former identifiers.
- Feature toggles: the docs do not say what happens to existing cycles, modules, views or pages, or to filters and Display options referencing them, when a feature is turned off. ui.md P3 mismatch #23 notes that the engine does not refuse cycle or module tools while a toggle is off.
- State delete: Plane documents 'move items first', not a move dialog. Tessera's delete_state already accepts move_to_state_id, which is a deliberate improvement.
- Timezone and cover image are General-tab fields in Plane, but Tessera's schema has neither (decision 6 says 'today' is the server's local date). Logo is a Phosphor icon plus a palette colour per the §1 scope row.
- docs.plane.so increasingly documents paid and Enterprise features (milestones, releases, workflows, PQL, governance). Only the CE-relevant parts are reported here.
- I did not read docs/contracts/service-api.md or tools.md in full, nor check that moveWorkItem's add/remove semantics match the label-drag fact; the orchestrator should confirm with the engine tests.

### Recommendations

- P4 views (lane F, /projects/[projectId]/views and /views/[viewId]): views list with search by name, a sort (manual sort_order, name, created, updated) and per-row '...' menu Edit, Duplicate, Lock/Unlock, Delete (confirm Dialog). The row shows the logo or icon, name, description excerpt, a lock icon when locked, and the item count from getCounts({type:'view'}).
- P4 view creation: 'Add view' Dialog (name required, description, layout, filters, display) and 'Save view' in the Work items filter row that opens the same Dialog prefilled from the current URL/view_settings state.
- P4 view detail: WorkItemsScreen in the view's layout with its filters and display. Local edits mark it dirty, and a dirty view shows 'Update view' plus 'Save as new view' (a Tessera addition, documented as such). Leaving without saving discards the edits (do not write them to view_settings for the view scope).
- P4 lock: a locked view hides 'Update view', Edit and Delete, and shows the lock icon and a read-only hint. Recommend still allowing unsaved local filter changes with 'Save as new view' (engine assertUnlocked already refuses update and delete). Unlock is open to the single user, since there is no creator distinction.
- P4 duplicate: duplicate_view names the copy 'Copy of <name>' with the same filters and display, and opens it.
- Drop personal/public access, sharing, publishing and per-view export permanently (single user; excluded in §1). View export goes to P10 with CSV/JSON exports. View favourites (star in list and header) go to P9 with favourites (§1, decision 1).
- P4 grouping: keep multi-valued grouping as built (labels, assignees and module duplicate an item into each group; a 'None' group for items with no value). On drop, move only the dragged-from value to the dropped-on value and keep the others. A drop onto None removes the source value; a drop from None adds the target. Enforce this in moveWorkItem and Vitest, label it a Tessera rule since the docs only confirm board label relabelling, and show a count in each group header.
- P4 sub-groups: board swimlanes only, matching the Plane docs; the list stays single-level. Sub-group fields follow Plane: state, priority, labels, cycle, module, assignees, created_by. Reconsider Tessera's extra state_group, created_at and target_date sub-group values or keep them as harmless extras. 'Show empty groups' applies to both axes.
- P4 counts: the sidebar project rows show open counts from getCounts({type:'project'}), and panel sub-headers and group headers use the same source (decision 21). Exit test: every rendered count equals getCounts for that scope.
- P4 settings General: name, identifier (decision 3 pattern, uniqueness CONFLICT message), description (MarkdownEditor compact), logo (Phosphor icon plus palette colour), Archive project (to /projects/archives) and Delete project (type the exact name to confirm). Identifier rename: keys stay computed, so /browse/NEW-n resolves at once. To make 'identifier rename keeps /browse' robust, add a small project_identifier_alias (former identifiers) lookup in /browse so OLD-n also redirects. That is a Tessera improvement; Plane does not document it.
- Defer the timezone field to P10 'remaining settings' (decision 6 uses the server local date) and the cover image (no attachments, U8) indefinitely. Also in P4: the read-only UI for archived projects (P3 deferral).
- P4 settings Features: toggles for cycles, modules, views, pages, intake and estimates. Turning one off hides navigation tabs, Power K entries, Display group-by options and filters for that feature, and keeps the data. Decide engine enforcement in P4 (ui.md mismatch #23): recommend refusing create tools with a RULE error and still allowing reads. Intake cannot be turned off while items are pending (already in the engine). Pages and intake toggles exist in P4 even though their screens land in P6 and P8.
- P4 settings States: groups shown in fixed order, '+' per group, inline edit (name, palette colour, description), drag reorder within the group (fractional sort_order), 'Mark as default'. Delete is disabled for the default state, the last state of a group and triage; deleting a state that holds items opens a move Dialog (choose a target state, via move_to_state_id). Changing a state's group by drag can follow in P10 if it is costly.
- P4 settings Labels: add (name, palette colour), edit, drag reorder, nest by drop onto a top-level label (one level), drag out to un-nest, and delete with a confirm warning that children and assignments are removed. CSV import is deferred indefinitely (not CE).
- P4 settings Agents tab (replaces Members): lists actors (user, assistant, each mcp:<name>), a per-actor 'may write' switch, the agent_intake_required switch (decision 27; effective once Intake lands in P8, so show it with a note or disabled until intake_enabled), and the default assignee selector (project.default_assignee_id, which can be an agent). No roles or invitations (excluded). Project lead is not needed.
- Defer to P8: estimates settings tab. Defer to P10: automations settings tab and rich filter tree (AND/OR/NOT). Defer to P9: workspace views and static views, favourites (views, cycles, modules), the sidebar project '…' menu, and the accordion vs horizontal navigation choice (Tessera keeps the tabs-in-panel-header model from the layout rework; no accordion).
- Also in P4, from the P3 deferral list in docs/contracts/ui.md 'Scope and deferrals': view_settings and saved-filter cleanup when a cycle, module, label or state is deleted (Plane removes deleted labels from views filtering on them); filters, display and layouts on Archives › Work items; search, sort and filter on the cycles and modules lists.

### Facts

- **Views: create from dialog**: Project › Views › 'Add view' opens a dialog. It has a name (required), a description (optional), an access level (public or private, shown as globe and lock icons), a layout, display options and filters (the filter builder). The button is 'Create View'. The new view appears in the project's views list. (https://docs.plane.so/core-concepts/views)
- **Views: create from current filters**: In the project's Work items you apply a layout, filters and display options, then click 'Save View'. The view takes the current filter selections. Display filters and properties start from the workspace defaults and can be changed later inside the view. The filter docs repeat this: 'Save view' keeps a filter combination as a custom view. (https://docs.plane.so/core-concepts/views ; https://docs.plane.so/core-concepts/issues/visualise_filter)
- **Views: layouts**: Project views support List, Board, Calendar, Table and Gantt. Workspace views use the spreadsheet (table) layout only. (https://docs.plane.so/core-concepts/views)
- **Views: editing a saved view**: You open the view and change its layout, filters or Display. An 'Update View' button then appears in the filter bar. Leaving without clicking it discards the unsaved filter changes, and the view reopens in its saved state. Display edits (Group by and the rest) also persist only when you update or save. The docs describe no 'Save as new view' action; the only way to get a second view from the same settings is Duplicate, then edit. (https://docs.plane.so/views ; https://docs.plane.so/core-concepts/views)
- **Views: editing from the list**: An older passage, quoted in a search-engine summary of the docs, says the views list has an 'edit view' option for changing the name, description and filters, and that any filter change prompts an update. The current page only says to open the view. Treat the edit-from-list dialog as plausible but unconfirmed. (https://docs.plane.so/core-concepts/views (search snippet))
- **Views: duplicate**: In the views list, the '...' menu or a right-click offers 'Duplicate' (also 'Make a copy'). The copy keeps the filters, display filters and display properties, and its name gets the prefix 'Copy of'. It can then be renamed and edited on its own. (https://docs.plane.so/core-concepts/views)
- **Views: lock (Pro in Plane)**: You lock a view with the 'Lock' button in its header or with '...' › 'Lock View' in the list. A lock icon then shows next to the name. A locked view cannot be edited: no filter changes, no display changes and no rename, even by its creator. Others still read it and see a read-only message. Only the creator unlocks it ('...' › 'Unlock View'). The docs do not say whether temporary, unsaved filter changes are allowed on a locked view. (https://docs.plane.so/core-concepts/views ; https://docs.plane.so/views)
- **Views: delete**: '...' › 'Delete' in the views list, then a confirmation. Deletion is permanent and removes only the saved configuration; work items are untouched. The four built-in workspace views (All Issues, Assigned to Me, Created by Me, Subscribed) cannot be deleted. (https://docs.plane.so/core-concepts/views)
- **Views: favourites**: You favourite a view by hovering it in the list and clicking the star, or with the star in the view header. Favourited views appear in the sidebar's 'Favorites' section. (https://docs.plane.so/core-concepts/views)
- **Views: access**: Views are public by default and visible to every project member. Private views (Pro) are visible only to their creator, and only the owner can change access. Sharing (Business), publishing (Pro) and export (Pro, CSV/XLSX/JSON, using the current session filters including unsaved changes) also exist. For single-user Tessera, access, sharing and publishing do not apply. (https://docs.plane.so/views)
- **Views list page**: The public docs do not describe the views list rows (columns or icons), search or sorting. The only documented row affordances are a hover star (favourite) and the '...' / right-click menu with Duplicate, Lock/Unlock View, Delete and Export. (https://docs.plane.so/core-concepts/views)
- **Display menu**: The Display menu has the sections 'Display properties', 'Group by', 'Sub-group by', 'Order by', and 'Additional options' with 'Show sub-work items' and 'Show empty groups'. Display properties are set per layout. (https://docs.plane.so/core-concepts/issues/display-options)
- **Display properties**: The CE-relevant properties are ID, Assignee, Start Date, Due Date, Labels, Priority, State, Sub-work item Count, Attachment Count, Link, Estimate, Modules and Cycle. Table also shows Created on, Created by and Updated on. Plane-only extras (Work item Type, Dependencies, Customer counts, Releases, Milestones) are outside CE. (https://docs.plane.so/core-concepts/issues/display-options)
- **Group by fields**: Group by accepts State, State groups, Priority, Cycle, Module, Labels, Assignees, Created By and None. Paid-plan-only options are Milestones, Releases, Work Item Types and Parent type. 'None' here means no grouping. (https://docs.plane.so/core-concepts/issues/display-options)
- **Sub-group by fields and layouts**: Sub-group by accepts State, Priority, Cycle, Module, Labels, Assignees, Created By and None; State groups are not listed. The views page says Sub-group by applies in the Board layout only, as swimlanes. List has no documented sub-groups. (https://docs.plane.so/core-concepts/issues/display-options ; https://docs.plane.so/core-concepts/views)
- **Order by**: Order by accepts Manual, Last Created, Last Updated, Start Date, Due Date and Priority, and applies within each group. (https://docs.plane.so/core-concepts/issues/display-options)
- **Show empty groups**: 'Show empty groups' toggles whether groups with no work items are visible. Its default is not documented. (https://docs.plane.so/core-concepts/issues/display-options ; https://docs.plane.so/core-concepts/views)
- **Drag between groups**: Board: moving a card between columns updates the property of that column (state when grouped by state). Labels: 'On the board, drag a work item between label groups to relabel it.' Calendar drag changes the due date; Gantt drag changes start and end. List allows reordering, but the docs do not say what a cross-group drop does in List. Nothing is documented for dropping into an assignee or module group, or into the None/no-value group. (https://docs.plane.so/core-concepts/issues/layouts ; https://docs.plane.so/core-concepts/issues/labels)
- **Multi-valued grouping**: No public doc says how an item with two labels, assignees or modules is shown when grouped. Duplicating the item into every matching group (Tessera's GROUPABLE_FIELDS comment) is a Tessera choice, not a documented Plane fact. Label docs: grouping by label works in board, list and spreadsheet. (https://docs.plane.so/core-concepts/issues/labels (silent on duplication))
- **Quick add in a group**: 'New work item' at the bottom of a list, group or column creates an item that takes the value of that group. (https://docs.plane.so/work-items/create-and-manage-work-items)
- **Filters**: Filters sit in a row below the toolbar; each condition is removed with X, and 'Clear all' resets. The CE-relevant fields are Title, State, State Group, Assignees, Priority, Mentions, Label, Cycle, Module, Start date, Due date, Created at, Updated at and Created by. The free plan uses the 'is' operator plus 'between' for dates. (https://docs.plane.so/core-concepts/issues/visualise_filter)
- **Project settings: General**: General has the project name (required), the identifier (required, for example PROJ-123, changeable later), a description, the access level (Public/Private), the lead, a timezone (affects cycle start/end times and project date displays; admin-only) and an icon/emoji plus a cover image. The button is 'Update project'. 'Archive project' and 'Delete project' sit at the bottom. (https://docs.plane.so/core-concepts/projects/overview ; https://docs.plane.so/introduction/tutorials/create-project)
- **Project identifier**: The identifier is auto-suggested from the name (WEB for Website Redesign); the tutorial advises 3–5 characters. The docs and the API reference state no length, character set or uniqueness rules. The docs do not say what renaming does to existing keys. A public forum thread reports that after a change most items were re-keyed but some old keys failed to resolve, which implies keys are re-derived, not kept as aliases. (https://docs.plane.so/introduction/tutorials/create-project ; https://developers.plane.so/api-reference/project/add-project ; https://forum.plane.so/t/missing-work-items-after-changing-project-id/295)
- **Archive / delete project**: Archive removes the project from the sidebar, search and active lists; it is restored from Projects › Archived projects › 'Restore project'. Delete is permanent: you type the exact project name, then click Delete, and work items, cycles, modules, views and pages are removed. (https://docs.plane.so/core-concepts/projects/overview)
- **Project settings: Features**: The Features tab has toggles that take effect immediately: Cycles, Modules, Views, Pages, Intake (off by default, admin-only) and Time Tracking (not CE). Project docs do not say what happens to existing data or navigation when a toggle is turned off. The workspace-features page says turning a workspace feature off hides it rather than deleting data, which is the closest analogue. (https://docs.plane.so/core-concepts/projects/overview ; https://docs.plane.so/core-concepts/intake ; https://docs.plane.so/workspaces/workspace-features)
- **States: groups and defaults**: There are five groups: Backlog, Unstarted, Started, Completed and Cancelled. The seed states are Backlog, Todo, In Progress, Done and Cancelled, with Backlog as the default. Only Completed counts as done for progress; only Completed or Cancelled items are eligible for auto-archive. Changing a state's group re-buckets its items. (https://docs.plane.so/core-concepts/issues/states)
- **States: add / edit / reorder**: The '+' on a group adds a state with a name (required, duplicates rejected), a colour and an optional description; the group is the one it is added in. Name, colour and description are editable at any time. Drag reorders within a group; dragging into another group changes the group. The last state in a group cannot be dragged away. (https://docs.plane.so/core-concepts/issues/states)
- **States: default**: 'Mark as default' on a state; the previous default is cleared, and there is always exactly one default. New items without a state get the default. (https://docs.plane.so/core-concepts/issues/states ; https://docs.plane.so/core-concepts/projects/run-project)
- **States: delete**: The default state, the triage state and a group's last state cannot be deleted. A state that still has work items cannot be deleted: Plane offers no automatic reassignment and no documented move dialog, so you move the items first. Deletion is permanent. 'Triage' is a reserved name, and the user cannot create states in the triage group. (https://docs.plane.so/core-concepts/issues/states)
- **Labels**: Project settings › Labels › 'Add label' takes a name (required, ≤255 characters, unique per project ignoring case) and a colour (random preset by default), then 'Add'. 'Edit label' changes the name and colour ('Update'). Dragging one label onto another nests it; the target becomes a collapsible parent, and nesting is one level deep. To un-nest, drag the label out. Drag also reorders, and that order is used in pickers and filters. Delete asks for confirmation and removes the label from every item and from views filtering on it. Deleting a parent also deletes its children. The name can be reused afterwards. Labels can also be created inline from a work item picker. (https://docs.plane.so/core-concepts/issues/labels)
- **Members tab**: The Members tab lists members with a role (Admin, Contributor, Commenter, Guest), Add member, and Remove (work items created by the removed member stay). It holds the Project Lead (informational) and the Default Assignee (applied to new items created without an assignee; None turns it off). (https://docs.plane.so/core-concepts/projects/manage-project-members ; https://docs.plane.so/introduction/tutorials/create-project)
- **Intake**: Intake is enabled per project from Settings › Features and uses a Triage state separate from the normal groups. Its statuses are Pending, Snoozed (Open), Accepted, Declined and Duplicate (Closed). Declined and Duplicate go to Cancelled. The docs say nothing on disabling Intake while items are pending, or on a pending count. (https://docs.plane.so/core-concepts/intake)
- **Sidebar navigation and counts**: Plane offers two project navigation modes: 'Accordion navigation control' (feature tabs nested under each project) and 'Horizontal navigation bar' (feature tabs at the top of the project view). Sidebar items can be hidden into 'More' and reordered, and 'Show limited projects on sidebar' shows the most recently accessed N. No public doc mentions work item counts in the sidebar or in group headers; Tessera's per-project sidebar count is a Tessera addition. (https://docs.plane.so/workspaces-and-users/customize-navigation)

## Product behaviour (public docs only)

I read the P4 engine in the working tree and ran the tests. All 9 matching test files pass (416/416).

What is already there:
- Views: list, get, create, update, duplicate ("Copy of <name>", then "(2)", "(3)"), lock, unlock, soft delete. A locked view rejects every change with LOCKED, except unlock. The tools exist (list_views to reset_view_settings, phase P4).
- view_settings: get, save (merges keys over the stored row) and reset.
- getCounts for six scopes: workspace, project, cycle, module, view and profile. Each call runs 6–7 grouped queries, about 0.7 ms on a tiny database. The sidebar's per-project totals come from listProjects counts, which is one grouped query for all projects, and a test already checks they match getCounts.
- Projects: update covers name, identifier, description, logo, default assignee and the auto-archive/auto-close fields. Feature toggles live in updateProjectFeatures.
- States: create, update, reorder, set default, and delete with a move target plus all four refusal rules.
- Labels: one level of nesting; deleting a parent deletes its children; delete strips the ids from items, pages, every view (locked ones too) and view_settings.
- Grouping: labels, assignees and modules repeat an item in every group it belongs to, plus a "none" group. moveWorkItem adds the new value and removes `from_value` instead of replacing.

Gaps the P4 UI will hit:
1. **Real bug (confirmed with a probe):** with scope "view", a caller's partial display resets the view's saved display to the defaults. `DisplaySchema.partial()` still fills defaults in zod 4. Saved order "-priority" plus caller `{group_by: "state"}` came back in sort_order.
2. **Identifier rename breaks old keys:** after renaming WEB to SITE, `WEB-1` returns NOT_FOUND, so old `/browse/WEB-1` links and `#WEB-12` mentions break.
3. **No reorderView**, although views have a sort_order (decision 4).
4. **Sub-grouped board drop is not atomic:** moveWorkItem changes only one group axis, so a drop that changes both column and swimlane needs two calls.
5. **Deleting a state, cycle or module leaves stale ids** in view filters and view_settings. ui.md schedules this cleanup for P4.
6. **No usage counts for the States and Labels settings screens:** deleteState counts archived items but getCounts does not, so a UI that relies on getCounts gets surprise `state_not_empty` errors.
7. **No actor write permission and no actor-scoped activity feed** for the Agents tab.
8. **search_all describes views but cannot return them.**
9. **rich_filters are stored but never evaluated**, which contradicts schema.md.
10. **Feature toggles are enforced only in the UI.**
11. **Group counts cover only the loaded page**, so they diverge from getCounts on large lists.

### Gaps

- GAP 1 (bug, view round-trip): with scope view, a partial caller display overrides the saved display with defaults. Fix: ListWorkItemsInput.display = DisplayPatchSchema.optional() (import from view-settings.ts); in resolveScope use `mergeDisplay(DEFAULT_DISPLAY, patch)` for the base and `mergeDisplay(DisplaySchema.parse(row.display), patch)` for view. No new tool; list_work_items picks up the input. No activity. Test tests/work-items.test.ts: 'view scope keeps saved display keys the caller omits' (saved {layout:'board', order_by:'-priority', properties:{key:false}}; call with display {group_by:'state'}; expect -priority order and groups by state). The UI must then send only changed keys.
- GAP 2 (exit criterion 'identifier rename keeps /browse'): old keys stop resolving after a rename. Proposal (no migration): `resolveRetiredIdentifier(ctx, identifier: string): ProjectRow | undefined` in projects.ts finds the newest activity row with entity_type='project', field='identifier', old_value=identifier, whose project is live and whose current identifier differs. A live project using that identifier always wins. getWorkItemByKey and getProject fall back to it before NOT_FOUND, so /browse/WEB-1 redirects to SITE-1's page. Alternative: a `project_identifier_alias(identifier, project_id, created_at)` table written by updateProject (needs a migration). No new tool (get_work_item_by_key and get_project cover it); the existing 'updated' identifier row is the activity. Test tests/projects.test.ts: 'renaming WEB→SITE keeps WEB-1 resolving to SITE-1; a new project WEB later takes WEB-1 over; renaming back works'.
- GAP 3: there is no view reordering. Add `reorderView(ctx, id: string, input: { before_id?: string; after_id?: string }): View`. Input: `ReorderViewInput = z.object({ before_id: IdSchema.optional(), after_id: IdSchema.optional() }).strict().refine(one required)`. It uses sortOrderForMove over listViews(scope), refuses ARCHIVED, and allows locked views (sort_order is not view content; note this in the schema.md Views section) or else rejects with LOCKED. Tool `reorder_view` (phase P4, mutates, input ReorderViewInput.extend({view_id})); add it to CONTRACT_PHASES and the tools.md row. Activity: verb 'updated', field sort_order, identifier = view name (as reorderState). Test tests/views.test.ts: 'reorderView moves a view between neighbours within its scope, refuses NOT_FOUND neighbours from another scope and VALIDATION for non-adjacent pairs'.
- GAP 4 (sub-grouped board drop): moveWorkItem changes one axis per call. Extend MoveWorkItemInput with `sub_group_by: GroupBySchema.optional()`, `sub_value: z.string().nullable().optional()` and `sub_from_value: z.string().nullable().optional()`. applyGroupChange runs once per axis in the same transaction (same RULE group_not_movable, VALIDATION when sub_group_by equals group_by). The move_work_item tool gets the fields automatically. Activity is the existing per-field 'updated' / label 'added'/'removed' rows. Test tests/work-items.test.ts: 'a board drop across column state and swimlane labels changes both in one call and is atomic on failure (archived module → nothing written)'.
- GAP 5 (promised P4 cleanup): deleting a state, cycle or module leaves its id in view filters and view_settings (labels already clean up). Generalise labels.ts stripLabelsFromViews/stripLabelsFromViewSettings into `stripIdsFromSavedFilters(ctx, input: { key: 'labels' | 'state' | 'cycle' | 'module'; ids: ReadonlySet<string>; project_id: string }): void` in a new saved-filters.ts. The name avoids the registry's mutation prefix, so it is internal. Call it from deleteState, deleteCycle (cycles.ts:719), deleteModule (modules.ts:566) and deleteLabel. One catch: the engine's sortOrderForMove refuses before_id plus after_id unless the two are adjacent in the project's flat order, and states and labels are shown grouped, so the UI must send only one neighbour. Four further findings for P4: (1) The drag hook keys item elements by item id. A board grouped by labels, assignees or module renders the same item in several columns, and the registrations collide. (2) A ListItem with href puts an invisible anchor over the row, and the hook's default ignoreSelector skips presses on 'a'. Link rows therefore need a drag handle, or must not be links. (3) AlertDialog takes only a string description, so delete-with-move must be a form Dialog, like TransferDialog. (4) The engine has no reorderView. For the settings sub-navigation there are two options: the Archives pattern (a TabList of href tabs in a PanelBar subheader) or the Astryx settings-sidebar template (a LayoutPanel holding a List of ListItems). For consistency with the rework I recommend the TabList.
