# Schema contract

Owner: lane A. Source folder: `src/lib/tessera/db/schema/` (Drizzle, SQLite; `index.ts` exports every table and the `schema` object). Migrations: `drizzle/*.sql` generated by `npm run db:generate` plus hand-written FTS migrations. This document is the contract every lane codes against; the Drizzle file is its implementation. Built in P1: every table below exists in `drizzle/0000_init.sql` (the FTS tables in `0001_fts.sql`); the service rules of later phases (pages, intake accept/decline, estimates, drafts) are not implemented yet.

## Conventions

- **Ids**: `id TEXT PRIMARY KEY`, UUIDv7 from `uuid` `v7()` (`core/ids.ts` `newId`), on every entity table. Exceptions: `activity.seq` and `notification.seq` are `INTEGER PRIMARY KEY AUTOINCREMENT` (append-only logs; the cursor) with a `uid TEXT UNIQUE` UUIDv7 alongside.
- **Audit columns** on every entity table: `created_at`, `updated_at` (ISO-8601 UTC text), `created_by`, `updated_by` (`actor.id`). The service fills them from `ctx`; callers never pass them.
- **Soft delete**: `deleted_at` on every entity table. Reads filter `deleted_at IS NULL` by default. Uniqueness is enforced with partial unique indexes `WHERE deleted_at IS NULL` so a deleted name can be reused.
- **Case-insensitive names**: tables with unique names carry `name_key` = lower-cased, whitespace-collapsed `name` (`core/keys.ts` `nameKey`), maintained by the service; the unique index is on `name_key`.
- **Enums** are zod enums in `src/lib/tessera/schemas.ts`, never SQL CHECK constraints.
- **JSON columns** use `text({ mode: "json" })` and a zod schema from `schemas.ts`; no JSON column is read without parsing through its schema.
- **Ordering**: `sort_order TEXT` holds a fractional-index key (`fractional-indexing`, wrapped by `core/order.ts`). Work items carry one project-wide key so the order holds under any grouping; a drop rewrites one row.
- **Dates**: `*_date` columns are `YYYY-MM-DD`; `*_at` columns are ISO-8601 UTC. "Today" is the server's local date (`ctx.today()`).
- **Colours** are palette keys (`PaletteColorSchema`), never hex.
- **Names**: snake_case, no SQL keywords (`state_group` not `group`; no column named `key`), foreign keys end in `_id`. The Drizzle binding of table `module` is exported as `moduleTable` (`module` is reserved in ESM); `view` is a reserved word in SQLite, raw SQL double-quotes it.
- **Foreign keys** are declared with explicit `onDelete`: `restrict` for `work_item.state_id` and `activity.actor_id`, `cascade` for children and junction rows, `set null` for optional references (`cycle_id`, `parent_id` on pages, `estimate_point_id`, `activity.project_id` / `work_item_id`).
- **drizzle-zod** is not used; hand-written zod schemas in `schemas.ts` are the public surface (`scripts/check-conventions.ts` would confine drizzle-zod to `db/schema/` if it were ever added).
- The Drizzle file may carry **additive** columns and indexes beyond the tables below (listed where they exist); the contract lists the minimum. Removing or renaming a listed column is a contract change.

## JSON shapes (`schemas.ts`)

- **Filters**: `{ state?: id[], state_group?: StateGroup[], priority?: Priority[], labels?: id[], cycle?: id[], module?: id[], parent?: id[], assignees?: id[], created_by?: id[], subscriber?: id[], mentions?: id[], project?: id[] (workspace views only), search?: string, start_date?, target_date?, created_at?, updated_at?, completed_at?: DateFilter, type?: null | "active" | "backlog", sub_items?: boolean, archived?: boolean, start_target_date?: boolean }` with `DateFilter = { op: "before" | "after" | "between", from?: date, to?: date, relative?: "today" | "1w" | "2w" | "1m" }`. Keys combine with AND; an id list matches any of its ids. `before` and `after` are strict, `between` is inclusive; `relative` wins over `from` / `to`; `between` + `relative` spans today..anchor; a `between` with one bound degrades to `after` / `before`; reversed bounds are swapped; timestamp columns are compared on the server's local calendar day; a `DateFilter` without a usable bound is ignored.
- **RichFilters** (stored since P1, evaluated from P10; UI in P10): `{ and: Node[] } | { or: Node[] } | { not: Node } | { field, op, value? }` with `field ∈ state, state_group, priority, labels, cycle, module, parent, assignees, created_by, subscriber, mentions, project, name, start_date, target_date, created_at, updated_at, completed_at, estimate_point`, `op ∈ eq, neq, in, not_in, is_null, is_not_null, contains, before, after, between` and `value: string | number | boolean | null | string[] | DateFilter`. `RichFiltersSchema` is written with a hoisted node schema so `z.toJSONSchema` converts it to a `$ref` into `$defs` without recursing; descriptions sit on the leaf fields, not on the recursive reference.
- **Display**: `{ layout: Layout (default "list"), group_by: null | GroupBy (default null), sub_group_by: null | "state" | "state_group" | "priority" | "labels" | "cycle" | "module" | "assignees" | "created_by" | "created_at" | "target_date" (default null), order_by: OrderBy (default "sort_order"), type: null | "active" | "backlog" (default null), show_empty_groups: boolean (default true), sub_items: boolean (default true), calendar: { layout: "month" | "week" (default "month"), show_weekends: boolean (default true) }, properties: { key, state, priority, labels, cycle, modules, assignees, estimate, start_date, target_date, sub_items_count, links, created_at, updated_at } (all default true except created_at and updated_at) }`. `GroupBy ∈ state, state_group, priority, labels, cycle, module, assignees, created_by, start_date, target_date, created_at, project`; `OrderBy ∈ sort_order, created_at, updated_at, priority, start_date, target_date, name, sequence_id, estimate`, each also with a `-` prefix for descending. `DEFAULT_DISPLAY` is the parse of `{}`.
- **DisplayPatch** (`view-settings.ts`): every `Display` key optional and without defaults; `calendar` and `properties` merge one level deep (`mergeDisplay`). It is the `display` input of `createView`, `updateView` and `saveViewSettings`; stored `display` columns always hold a complete `Display`.
- **CycleProgress**: `{ total, completed, cancelled, started, unstarted, backlog, by_state: Record<state_id, n>, by_label: Record<label_id, n>, by_assignee: Record<actor_id, n>, points?: { total, completed, cancelled, started, unstarted, backlog }, completion_chart: Record<date, pending> }` (`ProgressCountsSchema` + extensions). `ModuleProgress = ProgressCounts & { by_state, points? }` is a TypeScript type only.
- **Logo**: `{ icon: string (Phosphor name), color: PaletteColor }`.
- **AgentSettings** (decision 151): `{ runner_url: string, projects: { project_id: id, repo: string }[] }`. `AgentRunnerUrlSchema` accepts `http://127.0.0.1:<port>` and `http://localhost:<port>` (port 1 to 65535, optional trailing `/`); `AgentRepoSchema` accepts `name` or `owner/name` from `[A-Za-z0-9_.-]`, at most 140 characters, where no segment is `.` or `..` or starts with `-` and the owner starts with a letter, digit or `_` (the runner turns the repo into a folder path, so the schema keeps it inside one folder; review round, 2026-11-10); at most 50 projects. On read, a project entry with an unknown key or a bad repo is dropped (the schemas are strict) and a bad URL becomes `AGENT_RUNNER_DEFAULT_URL` (decision 151). `AGENT_RUNNER_DEFAULT_URL` is `http://127.0.0.1:3090`. Stored as given by `setAgentSettings`, normalised on read (`normalizeAgentSettings`).

## Invariants (service layer; each has a Vitest case)

Identifier and keys
- `identifier` matches `^[A-Z][A-Z0-9]{1,11}$` after upper-casing (`VALIDATION` otherwise); unique among non-deleted projects (`CONFLICT`, as is `name`); editable. The human key `<identifier>-<sequence_id>` is computed at read time; `getProject` accepts an id or the identifier in any case.
- `sequence_id` is allocated inside the insert transaction with `UPDATE project SET next_sequence = next_sequence + 1 ... RETURNING`; numbers are never reused, including after delete or move.

Projects and states
- `createProject` seeds Backlog (default, gray, `backlog`), Todo (blue, `unstarted`), In Progress (yellow, `started`), Done (green, `completed`), Cancelled (red, `cancelled`). Enabling Intake adds the hidden Triage state (`triage`; `CONFLICT` when a state named "Triage" exists); disabling Intake with pending or snoozed intake items is refused (`RULE intake_pending`), otherwise the triage state and the intake row stay. `agent_intake_required` has effect only while `intake_enabled` is on (the settings UI greys it out).
- Project counts (`Project.counts`, `getCounts`) count non-deleted, non-archived items outside triage; `by_state_group.triage` is always 0.
- On an archived project every mutation of its states, labels, cycles, modules, views and work items is `ARCHIVED`; only `unarchiveProject` and `deleteProject` are allowed. `unarchiveProject` on a live project is `RULE not_archived`. `deleteProject` soft-deletes states, labels, items (with junctions and FTS rows), cycles, modules, views, intakes and intake items in one transaction with one `deleted` activity row, and works on archived projects.
- `state_group` is immutable after creation (`UpdateStateInput` has no `state_group`); `createState` never takes `triage`. `setDefaultState` on the triage state is `RULE triage_default`.
- A state cannot be deleted when it is the default (`RULE default_state`), the triage state (`RULE triage_state`), the last state of its group (`RULE last_state_in_group`), or non-empty without a move target (`RULE state_not_empty`); the move target must be another state (`RULE move_target_self`) of the same project (`RULE move_target_project`) and not the triage state (`RULE triage_state`). Moved items (archived ones too) keep `completed_at` in step with the new group and get one activity row each.
- Exactly one default state per project; `setDefaultState` swaps atomically.

Labels
- One level deep: a label with a `parent_id` cannot be a parent (`RULE label_depth`), a parent must be in the same project (`RULE label_parent_project`), a label cannot be its own parent (`RULE label_self_parent`) and a label with children cannot be nested (`RULE label_has_children`). Names are unique per project (`CONFLICT`).
- Deleting a parent deletes its children. Deleting a label removes it from items and pages (junction rows hard-deleted), and strips its id from project views, workspace views and stored `view_settings` filters, each rewrite with an activity row. Deleting a state, cycle or module does **not** strip view filters yet (`filters.ts` tolerates unknown ids); P4 follow-up.

Work items
- Parent must be in the same project (`RULE parent_project`), not the item itself (`RULE parent_self`), and the parent chain must stay acyclic (`RULE parent_cycle`).
- `completed_at` follows the state group: set when moving into `completed`, cleared when leaving it.
- Archive only when the state group is `completed` or `cancelled` (`RULE archive_open_item`); archived items are read-only except unarchive and delete, including `subscribe` / `unsubscribe` (`ARCHIVED`). `unarchiveWorkItem` on a live item is `RULE not_archived`.
- Missing `state_id` on create falls back to the project default (`RULE no_default_state` when there is none). Creating or updating directly into the triage state is `RULE triage_state`.
- `createWorkItem` subscribes the creator and the assignees, and applies `project.default_assignee_id` when `assignee_ids` is omitted or empty.
- `start_date <= target_date` when both are set (`RULE date_order`).
- Labels, state, estimate point, parent, cycle and modules must belong to the item's project (`RULE label_project`, `state_project`, `estimate_point_project`, `cycle_project`, `module_project`); assignees must be non-deleted actors (`NOT_FOUND`). `setLabels` / `setModules` take up to 500 ids, `setAssignees` up to 100.
- `setAssignees` has replace semantics; adding an assignee auto-subscribes that actor. `subscribe` / `unsubscribe` default to the caller and are idempotent.
- Cycle guards on create and update: joining a cycle requires an open cycle (`ARCHIVED` / `LOCKED`) and an item that is not `completed` or `cancelled` (`RULE cycle_closed_item`); leaving or joining a completed cycle is `LOCKED`, an archived one `ARCHIVED`. `bulkUpdateWorkItems` applies one patch to 1..500 items under the same rules in one transaction.
- `moveWorkItem`: at least one of `group_by`, `before_id`, `after_id`. `value` null or `"none"` means the empty group; multi-valued groups (`labels`, `assignees`, `module`) add `value` and remove `from_value` instead of replacing; `state_group`, `created_by`, `created_at` and `project` groups are not movable (`RULE group_not_movable`). Neighbours must be in the same project (`RULE neighbour_project`), not the item itself and in order (`VALIDATION`); a single neighbour uses the real project-wide adjacent key.
- Reorders (`reorderState`, `reorderLabel`, `reorderCycle`, `reorderModule`): `before_id` is the row directly before the moved one, `after_id` directly after; with one side given the real neighbour fills the other; both given must be adjacent (`VALIDATION`); neighbours must be live (`NOT_FOUND`).
- Copies clear cycle, modules, estimate and assignees, append " (Copy)" to the name, keep labels, dates, priority and description, keep the parent and state within the same project (triage falls back to the default state), do not copy children, and log `copied`. Across projects the state maps by `name_key` (else the default), labels map by `name_key`, the parent is dropped.
- Moving to another project (`RULE same_project` when it is the same) allocates a new sequence, keeps the old key in activity (`verb moved`, field `project_id`, `old_identifier`), maps the state by name (else the default), maps labels by `name_key` and drops unmapped ones, clears cycle, modules and estimate, keeps assignees and subscribers, detaches children (one row each) and clears the parent. It is refused with `LOCKED` / `ARCHIVED` while the item sits in a completed or archived cycle (a deleted cycle pointer is cleared instead).
- `deleteWorkItem` soft-deletes the subtree, junction rows, FTS rows and the intake item, works on archived items and is allowed inside a completed or archived cycle.
- Description writes use compare-and-set on `description_version` (`CONFLICT` on a stale `expected_description_version`; an unchanged body is a no-op); property writes never bump it; activity stores the version numbers. The `work_item_version` row (collapsed per actor within 5 minutes) arrives in P10.
- Lists: `listWorkItems` with a `view` scope merges the caller's filters and display over the saved ones; workspace, profile and workspace-view scopes cover live, non-archived projects only; the `draft` scope is empty until P8; archived items appear only with `filters.archived` or the `archived` scope; triage items only when the filter targets the triage state.

Cycles (decision 16)
- Both dates or none; `start_date <= end_date` (`VALIDATION`). `status` is derived from the dates and today: `draft` (no dates), `upcoming`, `current`, `completed`.
- No overlapping non-archived dated cycles in a project, inclusive (`CONFLICT`); `unarchiveCycle` re-checks it.
- Names are not unique. Archive only after `end_date` (`RULE cycle_not_ended`); draft cycles cannot be archived. Completed cycles are read-only (`LOCKED`) except reorder, archive, transfer and deleting a work item that sits in them; archived cycles are `ARCHIVED` for everything but unarchive and delete. `deleteCycle` on a completed, non-archived cycle is `LOCKED` (archive first); it detaches the items with activity rows.
- A work item belongs to at most one cycle; adding replaces the previous cycle, which must be open too. Completed or cancelled items cannot be moved into a cycle (`RULE work_item_closed`), nor archived ones (`ARCHIVED`), nor items of another project (`RULE cycle_project_mismatch`). `removeWorkItemsFromCycle` works on editable cycles only. 1..500 ids per call.
- `transferCycleWorkItems` requires a completed, non-archived source (`RULE cycle_not_completed`), a target in the same project (`RULE cycle_project_mismatch`) that is open, and not the source itself (`VALIDATION`); it moves the incomplete items to the target (or to no cycle) and freezes `progress_snapshot` on the source the first time.
- Progress counts non-deleted items including archived ones and excludes triage (`getCounts` and module progress exclude archived items; intentional); `completion_chart` runs from `start_date` to `min(end_date, today)`, cancelled items excluded, by local day of `completed_at`; `points` in `points` mode only. The snapshot is frozen (issues mode, points included) on first transfer or at archive and served whenever non-null; live progress reflects later deletes, a frozen snapshot does not.
- `getActiveCycles` returns the current, non-archived cycles of live projects.

Modules
- Archive only when `status` is `completed` or `cancelled` (`RULE module_status`); archived modules are read-only except unarchive (`RULE not_archived` on a live module) and delete. Names unique per project (`CONFLICT`); `start_date <= target_date` (`VALIDATION`).
- Membership: items must belong to the module's project (`RULE work_item_project`) and exist (`NOT_FOUND`); adding an existing member or removing a non-member is a no-op; activity logs on both sides. `setModuleMembers` replaces the member list. `deleteModule` hard-deletes its junction rows and leaves `module_link` rows.
- Progress counts non-deleted, non-archived, non-triage items; `points` only when the project has estimates enabled and an estimate system.

Links
- `url` is an absolute http(s) URL of at most 2048 characters, `title` at most 500; a link belongs to exactly one work item or module (`VALIDATION`); archived parents and projects are read-only (`ARCHIVED`). Activity: `added` / `removed` with field `link`, updates with `link_title` / `link_url` / `link_metadata`.

Views
- Locked views reject every change except unlock (`LOCKED`); `lockView` on a locked view is `LOCKED`, `unlockView` on an unlocked one `RULE not_locked`. Names are unique per project and among workspace views (`CONFLICT`).
- `reorderView` is allowed on a locked view: `sort_order` is placement, not view content. Neighbours must be views of the same scope (the same project, or the workspace).
- `duplicateView` names the copy "Copy of <name>" (then " (2)", " (3)", ...), copies description, filters, rich filters, display and logo, leaves it unlocked and logs `copied`.
- Workspace views (`project_id NULL`) default to and accept only `layout: "table"` (`VALIDATION` at `display.layout`).
- `updateView` replaces `filters`, merges `display` (DisplayPatch), and clears `rich_filters` / `logo` with null. `saveViewSettings` merges filters key by key (an empty list clears a key) and display one level deep, and returns the merged result; `resetViewSettings` deletes the row; the workspace scope uses `scope_id = "workspace"` (`VALIDATION` otherwise).

Pages (P6)
- Archive propagates to descendants; a page must be archived before delete; children of a deleted page become top-level; locked pages are read-only; moving between project and wiki keeps the id.

Intake (P1 policy; accept, decline, snooze and duplicate in P8)
- When `intake_enabled` and `agent_intake_required` are on, an agent's `createWorkItem` lands in the triage state with a `pending` intake item (`source` from the input, default `mcp`); an agent's copy or move into such a project lands in Intake the same way; a person's create goes to the default state.
- Items with a pending or snoozed intake item cannot leave triage except via accept or decline (`RULE intake_pending` on `updateWorkItem` / bulk updates), and cannot be copied or moved to another project (`RULE intake_pending`).
- Accept sets the project default (or chosen) state and `status = accepted`; decline keeps the item in triage and hidden; snooze sets `snoozed_till`; duplicate sets `duplicate_to_id`; deleting a non-accepted intake item deletes the work item.

Estimates (P8)
- One active estimate system per project with 2 to 6 points; changing the type archives the old system and clears `estimate_point_id` on items.

Drafts (P8)
- "Move to project" creates the work item with its cycle, modules and labels and deletes the draft in one transaction.

Cross-cutting
- Every mutation runs in one `BEGIN IMMEDIATE` transaction and writes its activity rows inside it; `activity.seq` is the global cursor (`latestSeq`).
- Notifications (P7) are generated inside the same transaction as the triggering mutation (decisions 49-52). Never for the causing actor, system or assistant actors, or deleted actors, and never for the user when the assistant caused it. A new event merges into the recipient's newest row for the same work item and causing actor while it is unread, not archived, not snoozed and under 10 minutes old; the list orders by `sort_at`.
- Soft-delete cascades (project → states, labels, items, cycles, modules, views, intakes; item → children, junctions, intake item) run synchronously in the same transaction.
- FTS rows are written in the same transaction as the entity row; `search_all` and `filters.search` go through FTS5 (capped at 100 000 ids inside a list query), cycles, modules and projects are matched with `LIKE` on name (projects also on identifier).
- Second-process writes (`tests/concurrency.test.ts`, `tests/helpers/second-writer.ts`) are serialised by `busy_timeout`; a writer that waits longer gets `BUSY`.

## Migrations and database file

- `drizzle.config.ts` points at `src/lib/tessera/db/schema/index.ts`, output `drizzle/`. `npm run db:generate` creates a migration; `drizzle/0000_init.sql` is generated, FTS tables are added by the hand-written `drizzle/0001_fts.sql` (drizzle-kit does not model FTS5; `CREATE VIRTUAL TABLE IF NOT EXISTS`). `drizzle/meta/_journal.json` is read at runtime and must ship with the app; `REPO_ROOT` is found by walking up from the module to the folder that holds `drizzle/meta/_journal.json` and `package.json`.
- `getDb()` (in `db/client.ts`) resolves `TESSERA_DB_PATH` (default `data/tessera.db`) against the repo root derived from the module location, never `process.cwd()`; runs `migrateIfNeeded(filePath)` for file databases; then `openDatabase(filePath)` creates the folder, opens with `better-sqlite3`, sets `journal_mode = WAL`, `synchronous = NORMAL`, `foreign_keys = ON`, `busy_timeout = 5000`, applies pending migrations (`migrate`), ensures the FTS tables and the three system actors. `closeDb()` drops the singleton.
- `migrateIfNeeded(filePath, { lockTimeoutMs? })` creates `<file>.migrate.lock` exclusively (waits up to 30 s for another process, then `BUSY` naming the lock file; a lock left behind by a crash must be removed by hand), and when migrations are pending runs `VACUUM INTO data/backups/tessera-<iso>.db` first and keeps the newest 10 backups; returns `{ applied, backup, pruned }`.
- Only the Next server (`getDb`), `npm run db:migrate`, `npm run db:seed` and the stdio MCP entry with `--migrate` migrate. `scripts/mcp-stdio.ts` refuses to start on pending migrations without `--migrate` (exit code 2) and always logs the absolute DB path to stderr; `npm run db:fts-rebuild` refuses to run on pending migrations.
- A migration that recreates `work_item` or `page` must be followed by `npm run db:fts-rebuild`; `tests/fts.test.ts` guards that search works after all migrations.
- Tests open `:memory:` databases (`tests/helpers/db.ts` `createTestDb`, `createTestContext`) and apply all migrations through the same `migrate()` function; `withTempFileDb` covers the file path, lock and backup code.
- Node >= 22.14 (Node-API 10) is required by `better-sqlite3` 13; `.nvmrc` pins 22.23.3, `engines.node` enforces it, `vitest.config.mts` fails fast on an older `process.versions.napi`.
